Building Opus Brain: a multi-agent layer over a supply-chain network

Opus Brain is an intelligence layer over TraceLink's supply-chain network. A customer writes a metaprompt — a plain-language description of what they want an agent to do — and the platform runs it against their own supply-chain data: compliance audits, analytics, and the repetitive process work that piles up around purchase orders, invoices, and payment flagging.

I designed the orchestrator and the multi-agent architecture behind it, built the tool-calling layer, and wrote the evaluation setup. This is a look at the interesting decisions — especially why we built it in-house instead of reaching for an off-the-shelf agent framework.

The problem: the data model didn't fit the tools

The appealing pitch for agents is "point a framework at your data and let it reason." That breaks the moment your data isn't one clean store. Supply-chain objects at TraceLink live across separate applications, microservices, and databases — a purchase order, its line items, the invoice that references it, and the payment that settles it can each sit behind a different service with its own API and its own model of the world.

No off-the-shelf agent framework mapped cleanly onto that. So the real work wasn't prompt engineering — it was giving agents a faithful, governed way to reach a distributed data model, and being able to prove the answers were right.

The architecture: plan, act, validate

The orchestrator splits every request into three roles, so no single agent is doing everything at once:

Master planner

Decomposes the metaprompt into a structured plan — the sub-tasks, their dependencies, and what "done" looks like.

Tool-calling agent

Executes the plan by spawning a DAG of downstream calls — retrieval, data access, code — respecting dependencies between steps.

Validation agents

Check the output before it goes back to the user, so a plausible-but-wrong answer doesn't slip through.

Modelling execution as a DAG rather than a linear chain matters: independent sub-tasks can fan out and run concurrently, while genuine dependencies are still honoured. It also gives you a natural place to retry or short-circuit a branch without redoing the whole plan.

The tool-calling layer

Agents are only as capable as the tools you give them. I built the layer that lets the tool-calling agent actually do things against the network:

  • Knowledge retrieval — pull the right context out of the supply-chain data before acting on it.
  • CRUD / GraphQL generation — turn an intent into the concrete queries and mutations that hit the underlying services.
  • Code generation — synthesize logic for the analytical and process work that can't be expressed as a single query.
  • Memory manager — extract and track entities across steps so long-running tasks stay coherent instead of losing the thread halfway through.

The memory manager is the piece people underestimate. For a one-shot question you can get away without it; for a multi-step audit that touches dozens of related objects, you need a durable notion of "the entities we're working with" or the agent forgets what it was doing.

Why in-house on AWS Bedrock

Adopting a ready-made framework would have been faster to a demo and slower to a product. The distributed data model was the deciding factor: the abstractions a generic framework gives you assume a shape our data didn't have. Building on AWS Bedrock in-house was more upfront work, but it bought three things that mattered:

  • Control over tools — we could model access to each service and database exactly, instead of forcing it through a generic connector.
  • Control over memory — entity extraction tuned to supply-chain objects, not a generic vector dump.
  • Control over evaluation — we could wire correctness checks into the loop rather than bolting them on afterward.

Evaluation: deterministic checks + LLM-as-judge

For compliance and finance-adjacent work, "it usually looks right" is not acceptable. The evaluation setup combines two approaches over golden datasets:

Deterministic checks

For anything with a knowable right answer — did the numbers reconcile, did the query return the expected shape — assert it directly. Fast, cheap, and non-negotiable.

LLM-as-judge

For open-ended output where there's no single correct string, a judge model scores quality against a rubric — graded against golden examples to keep the judge honest.

The golden datasets are what make this trustworthy: they turn "the agent felt better this week" into a measurable regression suite you can run on every change.

What I'd carry to the next system

  • Separate planning from acting from checking. Collapsing them into one prompt is how you get confident, unverifiable answers.
  • Model execution as a DAG. It gives you concurrency, dependency-awareness, and clean retry boundaries for free.
  • Buy control where your data is weird. An off-the-shelf framework is great until your data model fights it; then in-house pays for itself.
  • Evaluation is a first-class feature, not a phase. Deterministic where you can, judged where you can't, golden datasets underneath both.

Opus Brain was the most end-to-end system-design work I've done: ambiguous requirements, a genuinely hard data model, and a bar for correctness that meant the evaluation harness was as important as the agents themselves.
